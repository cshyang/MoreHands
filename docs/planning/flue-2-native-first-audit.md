# Flue 2 Native-First Audit: what custom code to delete

**Date**: 2026-09-30
**Branch**: `flue-2-spike`
**Rule set by the owner**: stay native Flue. Custom code exists only to fill gaps Flue could not cover. If Flue 2.2.2 covers the need cleanly, delete ours.
**Method**: read the repo (`.flue/`, `src/`, `migrations/`, deploy glue, git history for why each piece was built), read the installed Flue docs and types in `spikes/flue2/node_modules/@flue/runtime/` (`docs/` and `dist/`), then ran real probes in `spikes/flue2/` (local `vite dev`, real model `zai/glm-5.3-flash`, one `zai/glm-5.2` turn, a local stall server, no production, no Slack).
**LOC**: counted from line ranges in the files, not whole files. Tests are counted where they test only the deleted code. Estimates within roughly 10 percent. "Net" means after adding the small replacement code.

## 1. Verdict

About 1,690 lines of infrastructure can go. About 890 of them go in the Flue 2 migration itself: burst-absorb (about 370, owner-approved native join), the stream-journal patch (190), most of the dead-turn reaper (about 110), the 6-hour heartbeat (about 30, pending the owner's log check), and five small wrappers (about 190 together). Another 800 lines are deletable only after a trigger: a container canary, a GitHub MCP canary, a read of the `@flue/slack` source, or a quiet month of logs. About 7,000 lines of custom infrastructure stay, and nearly all of that is product logic or integration that Flue has no feature for: agent-runs with Trigger.dev (3,063 lines alone), reminders, reflection and review sweeps, code-mode, the connection broker, and the Slack receipt UX. The owner-approved burst design has proven join mechanics but not yet a passing reply behavior: the 20-burst simulation missed its pass bar, so the absorb deletion is gated on a rerun with two guards (P-I). I pushed back on the principle in seven places where deleting would lose behavior or safety (section 2b).

Pass bar: zero lost messages, at most 2 reply rows in at least 90 percent of bursts, no duplicated answers, no reply loops. **Not met in any run. Best run (5): 3 lost, 12 of 20, 3 duplicate answers, 2 runaways.**

Failure modes, in order of size:

1. **Model answers in plain text instead of calling the reply tool (runs 1 to 4, and burst 20 in run 5).** Plain text is discarded, so the message is lost. glm-5.3-flash did it in about half the bursts, glm-5.2 in a handful. A "no reply in the whole response" check does not help when several messages joined, because one late reply satisfies it while the earlier joined messages were answered in plain text (run 4, burst 2: 3 of 4 lost). Run 5's check (no reply since the newest message) cut losses from 11 to 3, but burst 20 still lost 3 of 4 because the single reply answered only the last question.
2. **Z.ai rate limit (429, code 1302) on flash, even at concurrency 1.** A no-reply nudge loop burns requests and makes it worse (run 3: 111 nudges). This is a provider and model-choice problem, not a join problem. Flue retried 4 times in about 12 s, then settled `failed`.
3. **Reply-tool runaway.** Run 5, burst 18: 188 reply calls in one response until the provider stream errored. Run 4, burst 14: 6 calls for 3 messages with 3 duplicate answers. Nothing caps replies per response.
4. **Reply rows above 2 is mostly the design working.** With 3 to 4 messages at gaps of 1 to 4 s and a 5 to 10 s model call, the model answers at several boundaries, so a 4-message burst often yields 3 to 4 replies, each answering its own question (my "reply loops" column flags these, so I report runaways separately). The pass bar of at most 2 rows is hard to meet for 4-message bursts without holding replies back.

Smallest fixes, not applied or re-run: (a) cap the reply tool at N calls per response, refusing further calls with "end your turn" (kills failure mode 3). (b) Make the finish hook name the unanswered messages (the start seam stores each delivered text in persistent state; the hook lists those with no reply after them) instead of a generic "call reply" (targets mode 1). (c) Use a model that calls tools reliably; do not judge the design on glm-5.3-flash. Do not retry prompt wording: the earlier prompt fix already failed.

### 2a-2. P-J: debounce versus native join (flash only)

Same 26 bursts in every arm (the 20 bursts of P-I, same seed, 59 messages, 4 with a duplicate `event_id` redelivery, plus 6 single-message bursts: 65 messages), one burst at a time with an 8 s pause, model `zai/glm-5.3-flash` only. Reply layer held constant: reply tool capped at 2 accepted calls per response (then refused), and a `useAgentFinish` check that lists the unanswered messages by sender and text and sends the model back to work, skipped once the cap is hit. No prompt changes between arms. Bounded rate-limit handling: a burst whose submission settled `failed` with a 429 or 1302 is re-run (max 2, 30 s backoff); Flue exposes no model-call retry knob beyond its own 4 internal retries. Arms: **A** native join (instant ack and dispatch, later messages get eyes and join). **C** debounce only after a settle: instant like A, joins like A while a turn runs, but a message within 3 s after a settle starts a 2 s trailing window, then one ack and one dispatch. **B** trailing debounce: every idle-state message starts or extends a quiet window (1 s and 2 s arms), then one ack and one dispatch carrying all collected messages (`[sender] text` lines, key `batch:<event ids>`); messages during an in-flight turn follow A. The window timer is an in-memory loop in the dev server. One run per arm (model output is stochastic, so differences of a few bursts are noise). Clean runs: server started after the last file edit, no duplicate events (checked). Arm C first crashed on a dev-server connection reset at burst 1 of 26 and was rerun whole.

What the numbers say:

- **Flash dominates the result.** 9 to 21 submissions per arm ended because flash never called the reply tool and the finish check hit Flue's 32-cycle ceiling. That is the largest cause of lost messages in every arm and it is model behavior, not gateway policy. Provider 429s were rare once bursts ran one at a time (6, 0, 0, 3 failed turns); they are reported separately and did not cause lost messages.
- **The reply cap of 2 causes loss in 3 to 4 message bursts.** Every lost message in the healthy subset sits in a burst with cap hits (A 4 hits, C 15, B 7 and 14). When the model answers one question per reply, the third and fourth answers are refused. A cap of 2 is too low; it should scale with the number of delivered messages, for example deliveries plus one.
- **Debounce did not reduce extra replies or cost where it counts.** Bursts with at most 2 reply rows: A 18 of 20, B 1 s 19 of 20, B 2 s 20 of 20. That is one or two bursts, within run-to-run noise. In healthy bursts cost is identical (4.5 to 5.0 turns per burst in all four arms). B looks cheaper overall (8.0 and 10.4 versus 14.8 turns per burst) only because fewer bursts fell into the nudge loop (3 and 5 versus 9), which I cannot attribute to debouncing from one run per arm.
- **Latency.** Debounce adds its window. Multi-message first-reply medians: A 3.2 s, C 2.7 s, B 1 s 5.2 s, B 2 s 4.7 s; the gap is about the window plus noise. Single-message medians (A 8.0, C 9.7, B 1 s 5.7, B 2 s 5.0) move in the wrong direction for B and mostly reflect flash latency noise of 2 to 11 s per turn, so a 1 to 2 s window is not measurable here.
- **Policy C's window is rare.** It fired in 2 of 26 bursts (B3 and B8). That bounds its benefit at about 8 percent of bursts in this mix, and in those two it did produce one ack and one dispatch. Single-message latency stayed at A's level (9.7 versus 8.0 s median, inside flash noise) because C never holds a first message.
- Duplicate redeliveries were stopped at the event claim in every arm (4 of 4). No arm produced a duplicate answer.

**Verdict.** On this evidence debounce is not worth it. It does not measurably cut lost messages (the losses come from flash skipping the tool and from the cap), extra replies (at most one or two bursts in 20) or cost (equal in healthy bursts), and it costs 1 to 2 s of first-reply latency plus a durable timer. Keep Policy A, native join. Policy C adds custom code (a durable timer and batch store) for a window that opened in 2 of 26 bursts. Fix reply discipline instead: a cap that scales with delivered messages, and find a model or tool design that does not skip the reply tool.

**Durable timer, if you ever build B or C.** Flue has no delay or scheduled-delivery option on `dispatch()` (the `AgentDispatchRequest` fields are `id`, `message`, `initialData`, `uid`, `idempotencyKey`; I found nothing in `docs/` for delay). The nearest native piece is the Agents SDK `schedule()` through the per-module `extend()` hook (`docs/guide/schedules.md`, `docs/guide/cloudflare-target.md`), which runs inside an existing conversation's Durable Object and fires after a running response settles. That fits post-settle coalescing (Policy C) but not a pre-dispatch quiet window (Policy B), where no conversation exists yet. Either way it is custom code: a Durable Object alarm or `schedule()` callback plus a batch store, roughly 60 to 80 lines, not counted in the totals.

**Limits.** One run per arm. Flash may not represent the production model, and because flash often skips the reply tool the healthy subsets are small (17 to 23 bursts). The in-memory timer would not survive an eviction. The harness ran one burst at a time, so it does not test debounce under concurrent channels.

### 2b. Where I pushed back on the principle

1. **The silent-hang watchdog stays, slimmed.** Flue ends a hung turn only at the total wall-clock deadline, and only with a failure (P-C). Its real idle timeout exists only for the Workers AI binding provider, not for our OpenRouter or Z.ai calls. `timeoutMs` is a total budget, not a liveness check, so a value long enough for legitimate long turns makes a silent hang wait that long. Today a silent pre-token hang is caught in 3 minutes. Decide `timeoutMs` from reaper logs, and keep the first-token check until the trigger in row 5.
2. **The epoch reset stays.** Flue has no conversation delete, and a thread whose every call fails instantly is not retried. P-F suggests 2.x no longer poisons after a crash, so delete the automatic wedge counter after a quiet month, but keep the admin route and the epoch suffix.
3. **The KV event claim stays.** The claim at `.flue/app.ts:845` guards more than dispatch: the working ack post, the receipt, the transcript log. A native key dedupes only the dispatch, so a Slack retry would double-post "On it". The ambient path (`:787`) never dispatches at all. Only the `sched:` claim moves to a native key.
4. **Burst-absorb: approved native join, but the probe missed its pass bar.** Join, eyes, no-ack dispatch, sender attributes and duplicate handling all worked (P-I). What failed is model reply discipline, which the old absorb also depended on but hid behind the drain. Until a rerun passes with guards (a) and (b) from P-I, deleting absorb trades a working one-reply mechanism for a design that loses or repeats answers in the tail. Two couplings must be ported, not deleted: the gate reads receipt status from `submission_running` and `submission_settled` (not `updated_at`, which only the stream heartbeat kept fresh), and the reply tool's conversation id moves to `useDelivery()`.
5. **Native sandbox only behind a flag, and not before the audit exists.** Always-on attach boots the container on every turn (P-D). Native tools drop `coordinator_workspace_ops` and the secret redaction, which the ADR treats as a safety requirement.
6. **`VALIDATED_MODELS` is policy, not a workaround.** It records which models survived a real turn (the kimi and deepseek dead-on-arrival history). Only the window-warning half is obsolete. A bogus model id fails in about 30 ms (spike Retry ownership, D1), but the reason is only in server logs, so keep the write-time guard.
7. **Skills, not yet.** See row 9.

Also flagged, not assumed: the 6-hour heartbeat fan-out (`fireHeartbeat`, `0 */6 * * *`) wakes every project with no work. Reminders fire from their own minutely scan. It may be dead weight, but that is a product question for you.

## 3. New native features worth adopting (each removes code or risk)

1. `useAgentFinish` with `response.toolCalls` (P-E): replaces `withReplyReminder` with a hard check, bounded at 32 continuations. Also the seam for post-at-finish (P-B3).

3. `idempotencyKey` on every dispatch (P-A): Slack `event_id` on turns, `fireId` on scheduled fires, `retry:<id>` on any re-dispatch.
