# Flue 1.0.0-beta.1 — Spike Findings (2026-06-18)

**Historical reference (organized 2026-10-05):** These June spike findings describe Flue 1.0 beta. They are preserved for the migration rationale; current production uses Flue 2.2.2. See the [completed cutover](../../operations/2026-10-05-flue-cutover.md) for current evidence and the [deployment runbook](../../deployment.md) for operating instructions.

**Verdict: migration is viable via Path A and small.** In an isolated worktree off local HEAD (`e3d2328`), bumping `@flue/{runtime,sdk,cli}` to `1.0.0-beta.1` reached a **green `tsc` (0 errors), green `flue build --target cloudflare`, and a fully green test suite (58 files)** after three fixes. Total footprint: **29 files, ~231 insertions / 236 deletions** (mostly the mechanical `Type` repoint + lockfile churn).

Baseline before the bump was confirmed green on 0.11 (`tsc` 0 errors, build OK) so every break below is genuinely 1.0-introduced.

## Three breaks found (all fixed in the spike)

### 1. `Type` removed from `@flue/runtime` — 23 files (known)
`tsc` flagged exactly 23 `TS2305: Module '"@flue/runtime"' has no exported member 'Type'`.
**Fix (Path A):** repoint the import — move `Type` to a new line `import { Type } from '@earendil-works/pi-ai';`, leave the rest on `@flue/runtime`. Add `@earendil-works/pi-ai` as a direct dep (it's already a transitive dep of `@flue/runtime@1.0.0-beta.1` — `0.79.6`).
**Path A validated at runtime, not just types:** a probe built a tool with `parameters: Type.Object({...})` and 1.0's `defineTool` accepted it, emitting clean JSON Schema:
```json
{"type":"object","required":["who"],"properties":{"who":{"type":"string","description":"name"},"n":{"type":"integer","description":"count"}}}
```
1.0 docs confirm `defineTool` accepts raw JSON Schema. So the ~230 `Type.*` call sites need **no change** — only the 23 import lines. (Path B — valibot rewrite — remains the eventual canonical end-state, doable gradually post-bump; not needed for the bump.)

### 2. `FlueEvent` event taxonomy changed: `tool_call` → `tool` — 2 files
The advisor's "name survives ≠ shape survives" prediction landed here. 1.0's `FlueEvent` union dropped `'tool_call'`; the tool-completion event is now `type: 'tool'` (carrying `toolName`, `toolCallId`, `isError: boolean`, `result?`, `durationMs`). `'tool_start'` is unchanged.
- `src/slack/activity.ts:389` — `event.type === 'tool_call'` → `event.type === 'tool'` (the `isError`/`toolName` fields it reads still exist on the new variant).
- `src/slack/activity.test.ts:399` — same rename in the test fixture (production + fixture must stay consistent). This was the last red test (`0 !== 1`: error branch never fired against the stale fixture).

### 3. `patch-package` patch must be regenerated for 1.0 — highest-stakes finding
MoreHands patches `@flue/runtime` (via `postinstall: patch-package`) with `stripPartialContentForJournal`, which strips `partial.content` before the `StreamChunkWriter` journals stream events. **Without it, a long turn's 3s flush segment grows O(deltas × message-length), crosses DO SQLite's ~2MB value ceiling (SQLITE_TOOBIG), latches the writer to `failed`, and makes the turn unrecoverable.** This is a correctness/durability fix, not cosmetic.

- The 0.11 patch targets a content-hashed dist file (`sandbox-B4vW9Ijf.mjs`); `patch-package` keys patches by version, so a bump silently drops it.
- **The bug persists in 1.0.** The `StreamChunkWriter` is byte-for-byte the same at the patch site (`write()` → `this.pending.push(event)` → 3s `flush()` → `appendStreamChunkSegment(..., JSON.stringify(events))`), and 1.0 ships **no** native `stripPartial`/size-guard. The Durable Streams rewrite did not fix this.
- **The patch ports cleanly** — same insertion point, new file `persisted-image-placement-qyxGKalp.mjs`. Regenerated as `patches/@flue+runtime+1.0.0-beta.1.patch`:

```diff
--- a/node_modules/@flue/runtime/dist/persisted-image-placement-qyxGKalp.mjs
+++ b/node_modules/@flue/runtime/dist/persisted-image-placement-qyxGKalp.mjs
@@ const STREAM_FLUSH_INTERVAL_MS = 3e3;
+function stripPartialContentForJournal(event) {
+	if (!event || typeof event !== "object" || !event.partial || typeof event.partial !== "object") return event;
+	return { ...event, partial: { ...event.partial, content: [] } };
+}
@@ write(event) {
-		this.pending.push(event);
+		this.pending.push(stripPartialContentForJournal(event));
```
Reproduce in Phase 1: re-apply that edit to the new dist file, then `npx patch-package @flue/runtime`. (The hashed filename `persisted-image-placement-qyxGKalp.mjs` may change in later betas — re-locate by grepping dist for `STREAM_FLUSH_INTERVAL_MS`.)

- **The patch-guard test was itself version-coupled** and must be de-coupled: `src/shared/patch-guard.test.ts` only scanned `sandbox-*.mjs`. Changed to scan all `*.mjs` in dist so it survives future bundler reshuffles:
```diff
- const files = readdirSync(distDir).filter((f) => f.startsWith('sandbox-') && f.endsWith('.mjs'));
+ const files = readdirSync(distDir).filter((f) => f.endsWith('.mjs'));
```

## Confirmed UNCHANGED (no migration work)
- **Generated deploy config identical to 0.11.** `flue build` produced the same DO bindings (`FLUE_PROJECT_AGENT`/`FlueProjectAgent`, `FLUE_REGISTRY`/`FlueRegistry`, `SANDBOX`/`Sandbox`) and the same migration history (`flue-class-FlueRegistry`, `flue-class-Project`, `sandbox-class`, `flue-011`). **No new DO migration appended → production cutover won't trigger a class change.**
- `.flue/` source root, `flue.config.ts`, custom `app.ts` + `cloudflare.ts`, agent discovery (`project`) — all work on 1.0.
- `agents@0.15.0` satisfies the 1.0 peer. `registerProvider`/`defineTool`/`ToolDefinition`/`FlueContext` signatures unchanged.
- `sql-storage.d.mts` byte-identical 0.11↔1.0 → stored session history should survive.

## NOT proven by the spike — must verify in staging (Phase 1 T5)
The spike ran build/typecheck/tests + a `flue dev`-free runtime probe. It did **not** run a live worker, so these remain open (as the plan anticipated):
1. **Runtime execute-gating** — that 1.0 actually *rejects* bad tool args end-to-end (the JSON Schema is well-formed and accepted; high confidence, but not driven through a live turn).
2. **`cloudflare.ts` cron `scheduled`** actually fires on 1.0 (build recognizes the entry; runtime untested).
3. **`getSandbox` / container exec** on 1.0 (needs Docker; not run).
4. **Real-DO-state session readability** + the in-flight-turn boundary at the cutover instant (storage schema is identical → high confidence; the existing dead-turn reaper covers in-flight drops).
